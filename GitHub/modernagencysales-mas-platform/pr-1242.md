## Summary

After PRs #1237 (5-phase fix) and #1240 (workspace_id on transient engagement), the live cascade run for ajmal@maestrogtm.com still hit:

\`PROVIDER_REQUEST_FAILED: Access denied to team 72054d35-d240-4c43-902a-173e7fdc835c\`

at build_lead_list / lead_magnet / build_funnel / campaign_setup. Root cause is one layer deeper than the transient-bridge:

The Launch Pad cascade calls mcp-server with \`MAESTRO_MCP_API_KEY\`. That key is owned by user \`f454a752\`. mcp-server's \`fetchAccessibleTeams()\` derives \`accessibleTeamIds\` from **the API key owner's** \`accounts_memberships\` rows. If the operator (\`f454a752\`) isn't a member of the calling user's workspace, every MCP tool call is rejected.

## Fix

Add \`accounts_memberships\` row \`(user_id=f454a752, account_id=<every non-personal account>, account_role='editor')\` so the operator can reach every workspace the launch-pad cascade routes to.

- **Backfill**: \`INSERT … ON CONFLICT DO NOTHING\` for every existing non-personal account
- **Trigger**: \`AFTER INSERT ON accounts\` adds the operator to new workspaces at creation time
- Idempotent — re-runs are safe
- Membership only — doesn't change ownership, billing, or primary_owner. Operator gets r/w via the existing \`can_access_team(team_id)\` RLS predicate
