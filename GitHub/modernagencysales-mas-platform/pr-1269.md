# fix(mcp,funnels): expose redirect fields + allow cross-workspace form attach

PR #1269 in modernagencysales/mas-platform — closed — by kimprobably — [https://github.com/modernagencysales/mas-platform/pull/1269](https://github.com/modernagencysales/mas-platform/pull/1269)

## Summary

Three related bugs surfaced while building a lead-magnet funnel end-to-end via the MCP API (live debugging session, 2026-05-25). All three were workarounds I had to apply via raw SQL because the MCP surface couldn't express the operation.

### 1. MCP `funnel update` schema missed 15 first-class columns

The app-side `updateFunnelSchema` accepts these fields, but the MCP `funnel` tool only surfaced opt-in/thank-you copy + qual-form-id. Missing on MCP:

`redirectTrigger`, `redirectUrl`, `redirectFailUrl`, `sendResourceEmail`, `doubleOptinEnabled`, `bootcampInviteCode`, `homepageUrl`, `homepageLabel`, `primaryColor`, `backgroundStyle`, `fontFamily`, `logoUrl`, `defaultLocale`, `optinHeadline`, `optinButtonText`, `thankyouHeadline`.

Symptom: agents trying to wire the canonical "qualify → redirect to thank-you page with resource URL" recipe through MCP had no path. Fix: add all the missing fields to `packages/mcp/src/tools/funnel.ts` inputSchema (LLM-visible) and `packages/mcp/src/validation.ts` Zod validator. `redirectTrigger` enum mirrors the app's exact tokens `none|immediate|after_qualification` — anything else 400s at the app boundary.

### 2. `getQualificationForm` rejected user-owned forms living in other workspaces

For `team` scope, the form lookup matched only `(workspace_id = X AND account_id = Y)` strict equality plus a legacy `workspace_id IS NULL` branch for pre-Tranche-D rows. A form owned by the same user but stored in a different one of their workspaces (e.g. canonical public account vs. an agency-linked client workspace) couldn't be attached to a funnel in the current workspace.

Symptom during the debug session: 404 "Qualification form not found" when attaching `f2d7c3c5-…` (owned by Tim, in his canonical `cae7cb6a-…` workspace) to a funnel in his Zeno Consulting workspace `067c34ee-…`. The MCP `list_forms` happily returns the form by user_id, but the attachment endpoint rejected it on team-id mismatch.

Fix: add `user_id == scope.userId` as a third OR-branch in the team-scope path. Strictly tighter than the personal-scope path (which already accepts any form owned by the acting user) — no new privilege.

### 3. Workspace-resolution clarity for magnet + funnel create

The session default for agency-linked operators lands on the most-recently-used client workspace, NOT the user's canonical public account. The funnel create response already carries `_effective_workspace.slug`, but nothing in the tool descriptions told agents that the public `/p/{slug}/{magnet_slug}` URL would track that slug. Agents building lead magnets for the canonical `/p/{username}/...` surface kept publishing them under client workspace slugs and watching the canonical URL 404 (this is exactly what happened during the debug session — the `5-day-ai-cold-email-sprint` funnel landed in Zeno Consulting and `/p/modernagencysales/5-day-ai-cold-email-sprint` 404'd until I moved it via SQL).

Fix: documented the resolution rule in both `funnel.create.slug` and the `magnet` tool top-level description, with explicit guidance to pass `team_id` when the canonical surface is the intended target.

**Why no default change:** agencies legitimately want client-workspace creation when operating on behalf of a client. A unilateral default flip would break that. Making the consequence visible in the tool description is the surgical fix.
