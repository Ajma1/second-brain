# fix(mcp-server): align DCR approval gate with advertised scope catalog

PR #1268 in modernagencysales/mas-platform — closed — by kimprobably — [https://github.com/modernagencysales/mas-platform/pull/1268](https://github.com/modernagencysales/mas-platform/pull/1268)

## Summary

- `STANDARD_SCOPES` was `{'mcp', 'offline_access'}` while the AS advertises 6 scopes via RFC 8414 discovery (`mcp`, `mcp:read`, `mcp:write:posts`, `mcp:write:campaigns`, `mcp:write:contacts`, `offline_access`)
- Well-known MCP clients (Claude Code, Cursor) read discovery and request the full advertised set; the DCR gate flagged 4 of the 6 as elevated and queued every legitimate registration as `pending`
- Each new client session generates a new `client_id` (random loopback port), so the queue grew unbounded with legitimate Claude Code registrations no operator could keep up with — full token-issuance lockout for the canonical happy path
- Fix: source `STANDARD_SCOPES` from `OAUTH_SUPPORTED_SCOPES` in `scope-catalog.ts` so the gate auto-syncs with what discovery advertises. Manual review now fires only on scopes outside the catalog (`admin`, `full_access`, `mcp:write:billing`, …) — the threats the gate was actually designed for

## Incident context

Tim hit `Client registration is pending operator approval. Tokens cannot be issued yet.` reconnecting Maestro MCP from Claude Code on 2026-05-25. All `Claude Code (maestro)` rows in `oauth_dcr_approval_queue` were manually approved as the operational unblock; this PR is the durable fix so it doesn't recur on the next `/mcp` reconnect (which always issues a fresh `client_id`).
