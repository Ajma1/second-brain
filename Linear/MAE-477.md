# Fix Brain page navigation under WorkOS AuthKit

- **Identifier:** MAE-477
- **Status:** Done
- **Assignee:** Tim Keen
- **Team:** MAE
- **Updated:** 2026-07-17
- **URL:** https://linear.app/modern-agency-sales/issue/MAE-477/fix-brain-page-navigation-under-workos-authkit

## User report

On staging, selecting another page from a Brain document does not navigate to the requested page.

Affected example:

* [https://staging.maestrogtm.com/brain/untitled-557c6c4d5b11](<https://staging.maestrogtm.com/brain/untitled-557c6c4d5b11>)

Browser console repeatedly reports:

`workos_initial_auth_http_failure: AuthKit middleware is not configured`

## Root cause

Universal TanStack route loaders call `getAuthKitContext()` directly. That API is only valid inside the server request-middleware lifecycle. Client-side router reloads therefore lose the middleware context and reset auth during Brain page selection.

## Scope

* Seed the root AuthKit provider through WorkOS's sanitized RPC-safe server function.
* Resolve protected-route auth through the WorkOS server function that supports client navigation while preserving Convex SSR auth.
* Keep access tokens out of returned loader data.
* Add regression tests and an ESLint ratchet preventing direct WorkOS request-context use in universal web loaders.
* Preserve the explicit server-only auth cutover evidence handler.

## Acceptance criteria

* Clicking a different Brain page updates the route and displays that page.
* Direct Brain deep links continue to authenticate.
* Client navigation does not emit `AuthKit middleware is not configured`.
* Unauthenticated protected routes still redirect to sign-in with the return path.
* Auth tests, frontend boundary tests, typecheck, production build, formatting, lint, and Knip pass.
