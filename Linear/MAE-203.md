# [ARCH-014] Close Convex runtime adoption hardening decision

- **Identifier:** MAE-203
- **Status:** Done
- **Assignee:** —
- **Team:** MAE
- **Updated:** 2026-05-21
- **URL:** https://linear.app/modern-agency-sales/issue/MAE-203/arch-014-close-convex-runtime-adoption-hardening-decision

## Context

Temporal is the current working hypothesis for Maestro V2 content workflow authority, but Hatchet may be better for us. Hatchet's official durable-execution materials claim durable task invocation storage, transactional event logs, checkpoint/resume, built-in monitoring/replay, native workers, Postgres-backed state, streaming, OpenTelemetry, rate limits, priorities, and simpler operational entry. We need a clean evaluation that does not privilege Temporal because it was considered first.

Planning docs:

* `docs/operator/plans/active/2026-05-21-maestro-v2-content-runtime-architecture.md`
* `docs/operator/plans/active/2026-05-21-temporal-adoption-program.md`

## Scope

Run a neutral decision process using the same Maestro workload for both systems:

* streaming provisional content
* persisted object versions
* deterministic gate execution
* repair attempt and re-check
* human approval/edit wait
* export blocked until ready
* worker crash/restart recovery
* replay/reconnect behavior
* observability/evidence trail
* self-host/deployment complexity
* agent training and static-gate burden

Evaluate Hatchet for two roles independently:

1. User-facing content runtime authority.
2. Internal Fabro/agent-swarm durable task execution.

## Acceptance Criteria

* Decision note compares Hatchet and Temporal against Maestro's actual content-object workflow, not generic marketing claims.
* [MAE-208](https://linear.app/modern-agency-sales/issue/MAE-208/arch-019-build-side-by-side-hatchet-and-temporal-content-runtime) side-by-side bakeoff results are included before a final recommendation.
* Recommendation explicitly states: Hatchet runtime replacement, Temporal retained, split architecture, or more testing required.
* Comparison covers deterministic state guards, streaming replay/reconnect, gate evidence, repair loops, HITL, observability, self-hosting, deployment, and agent training complexity.
* No runtime is selected unless it can enforce `ready` state and export/sync/publish guards with deterministic evidence.
