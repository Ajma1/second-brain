# [DX] Non-blocking taste nit fixer bot

- **Identifier:** MAE-349
- **Status:** Backlog
- **Assignee:** —
- **Team:** MAE
- **Updated:** 2026-06-19
- **URL:** https://linear.app/modern-agency-sales/issue/MAE-349/dx-non-blocking-taste-nit-fixer-bot

## Why

The taste judge can pass a PR while still returning useful `nit` findings. Those findings are not urgent enough to block merge, but they are often good cleanup ideas. We should preserve them and optionally let an automation fix them in separate low-risk PRs.

Source observation: Buildkite taste run for workflow observability PR #294 / build #1011:
[https://buildkite.com/mas/maestro-ci/builds/1011/list?sid=019edfa7-5233-4206-97f9-217851fb695a&tab=output](<https://buildkite.com/mas/maestro-ci/builds/1011/list?sid=019edfa7-5233-4206-97f9-217851fb695a&tab=output>)

## Desired behavior

Create a non-blocking taste-nit follow-up path:

* Taste `nit` findings keep the taste verdict as `pass`; they must not block merge.
* The CI artifact / Buildkite metadata / PR comment remains machine-readable enough to ingest after the run.
* A follow-up bot can collect passed-with-nits verdicts and either:
  * create/update a Linear issue with grouped nits, or
  * open small cleanup PRs when the change is mechanical and low-risk.
* Generated fix PRs should be separate from the feature stack and should not delay the original stack.
* The bot should dedupe repeated nits by file + line + issue text and avoid reopening the same cleanup forever.
* Riskier suggestions should stay as backlog comments/issues, not automatic edits.

## Acceptance criteria

* We can run or trigger a bot/script that reads the latest taste verdict JSON from a PR/build and emits a normalized backlog item list.
* The bot treats `nit` as non-blocking and never fails the original PR.
* The bot dedupes existing Linear entries/comments for the same nit.
* The first implementation can be conservative: capture to Linear only; auto-fix PRs can follow once dedupe and scope rules are explicit.
