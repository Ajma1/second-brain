Source spec: `docs/superpowers/specs/2026-06-28-linkedin-beneficial-adjacency-map-design.md`

## Goal

Run the implemented beneficial adjacency pipeline on the current LinkedIn corpus artifacts and produce a pilot artifact directory for review.

## Files/Artifacts

Use current corpus analytics artifacts as input. Write a run directory such as:
`artifacts/linkedin-corpus-analytics/pilot-2026-06-27/beneficial-adjacency/`

Expected artifacts include:

* `lineage_manifest.json`
* `run_config.json`
* `stage_state.json`
* `privacy_manifest.json`
* `budget_ledger.json`
* `engagement_sample_plan.csv`
* `embedding_inputs.jsonl`
* `embedding_cache.jsonl` if embedding mode is enabled
* `creator_embedding_edges.jsonl` if embeddings are available
* `creator_nodes_v2.csv`
* `creator_edges_v2.csv`
* `beneficial_adjacency_recommendations.csv`
* `low_confidence_candidates.csv`
* `beneficial_adjacency_review_queue.csv`
* `beneficial_adjacency_eval_summary.json`
* `observability_summary.json`

## Work

Run the CLI in plan/analyze/review modes first. Only run provider-touching embed or engagement stages if budget ledgers predict safe usage and dry-run output looks correct.

## Constraints

* Do not use Convex for analytics computation.
* Do not make broad Harvest calls; sampling must remain sparse.
* Provider keys/secrets must not be printed or committed.
* Over-budget provider stages should abort before calls and record the abort reason.

## Verification

Run appropriate smoke checks using `rtk`, for example:

```bash
rtk ls artifacts/linkedin-corpus-analytics/pilot-2026-06-27/beneficial-adjacency
rtk rg "scoring_version|review_status|known_limitations" artifacts/linkedin-corpus-analytics/pilot-2026-06-27/beneficial-adjacency
```

## Acceptance Criteria

* Pilot artifacts are generated with lineage, privacy, budget, and review files.
* Recommendations include score components, evidence, confidence, limitations, and review status.
* Any skipped provider stages are explicitly recorded in budget/stage state.
