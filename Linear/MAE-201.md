## Context

Temporal will be a core product runtime dependency. The software factory needs deterministic review rules so generated Temporal code follows safe workflow boundaries, test expectations, and evidence policy.

Planning doc: `docs/operator/plans/active/2026-05-21-temporal-factory-daytona-integration.md`

## Scope

Add factory/human review gates for Temporal-backed changes.

Required rules:

* Workflow code has no direct provider, DB, filesystem, HTTP, or event-stream I/O.
* Activities own all external effects and have explicit timeouts/retries.
* Workflow IDs are business meaningful.
* Task queue names are stable and documented.
* Workers polling the same task queue register the same workflow/activity types.
* Tests prove crash/restart behavior or use Temporal's test environment where appropriate.
* Content workflow history records state/version/gate decisions, not token deltas.
* Daytona smoke evidence exists before a Temporal workflow is accepted.

## Acceptance Criteria

* A review checklist exists in the planning docs or coding repo doctrine.
* Fabro can fail a Temporal workflow PR/build for missing timeout/retry policy, illegal workflow I/O, missing tests, or missing smoke evidence.
* Evidence schema includes workflow id, run id, task queue, final state, gate report refs, event history summary, logs, and replay/determinism result.
* The gate policy distinguishes product runtime evidence from factory build/release evidence.
* The rules are linked from the Temporal adoption program and factory/Daytona integration plan.
