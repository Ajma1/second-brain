## Decision (2026-06-08): standardize on PostHog, not Braintrust

Spiked Braintrust deeply (capture seam + prompt versioning — both proven, kept below as context), then chose **PostHog** as the LLM-observability + experimentation + analytics platform and **build the one missing piece ourselves** (an offline judged-eval CI guardrail). Braintrust dropped as a runtime dependency.

### Why PostHog

* Native **AI observability / traces** (`$ai_generation`/`$ai_span`/`$ai_trace`, cost/latency/tokens, OpenRouter), **flag-driven online A/B**, and **product analytics** — dual-use, one vendor.
* `@posthog/convex` (GA, Convex 1.39+): default isolate (no `"use node"`), **non-blocking** capture (`ctx.scheduler.runAfter`) — never on the request path.
* `$ai_*` events are plain events with special property names → emit via the component's `capture()` from a Convex action.

## Prompt versioning + measurement model (REVISED 2026-06-09)

> Refined after reading the actual workflow prompts. The earlier "store prompt versions as repo files + serve via flag payloads" framing was wrong on two counts: the prompt *content* already lives in a versioned table, and the judge is the wrong optimization metric.

### The prompts are two layers

* **Scaffolding** (`build*Prompt` templates, hook archetypes, rubric structure) → **git** (a deploy/`codeBuild` id).
* **Content** (judge rubrics, tells, soft-style notes, voice brief, templates) → the `methodologies` **table**, which **already has a** `version` **field** (per agency). That's the content registry.

A run's true prompt version = **(codeBuild) × (methodologyKey, methodologyVersion)**.

### Unit of change = a component overlay, NOT a methodology bump

Bumping the whole methodology to change one rubric makes attribution useless (hook/body/judge/revise all "change" at once). Instead: methodology + git are the **baseline**; an **experiment overlay** changes exactly one component (a rubric, the hook scaffold, …). A **PostHog flag assigns control vs the overlay**; the run records `(methodologyVersion, codeBuild, experimentId)`. Change one thing, hold the rest, attribute cleanly. (Flags carry a small variant id — not a whole prompt.)

### Measurement hierarchy — use what's available when

| Signal | Reliability | Latency | Role |
| -- | -- | -- | -- |
| **Human edit rate / acceptance** (`editEvents`) | high | at review | **the near-term A/B metric** (available now) |
| **Real engagement** (`contentObjects.metrics`) | ground truth | days + needs volume | long-term verdict; validates the proxies |
| **Judge score** (`hookJudge` / `runAiJudge`) | proxy (validate it) | seconds | **CI guardrail** + fast pre-signal — *not* the optimization target |

* The **judge is a guardrail, held FROZEN** while measuring other prompts. Validate it periodically: does a higher judge score actually predict less human editing / more engagement? If not, fix the grader first.
* **Optimize toward edit-rate now, engagement later** — never toward the judge (you'd be grading the grader with itself).

### PostHog's role vs ours

* **PostHog:** trace attribution (`$ai_trace`/`$ai_generation`), flag-assigned A/B + experiments, engagement analytics.
* **Ours (Convex / CI):** the **offline judge-guardrail** (`tsx` + a fixture dataset + a frozen judge, fail-CI-on-regression) and **edit-rate attribution/analysis** (from `editEvents`).

### Build the measurement SPINE first — before iterating on any prompt

1. **Attribution** — stamp `(methodologyVersion, codeBuild, experimentId)` on the `postRuns` row + the `$ai_trace`.
2. **Edit-rate capture** — record human edits per run (`editEvents`), attributed to the experiment. The immediate A/B signal.
3. **Offline judge-guardrail** — `tsx` + a fixture set + frozen judge; fails CI on hard-rule regressions (grounding / format / voice).
4. **PostHog trace capture** — `$ai_trace` per run via `@posthog/convex` + in-flight scores as props; publish-time engagement events.

Then iterate: the guardrail catches regressions pre-merge, edit-rate says what's better now, engagement validates it over time.

### First slice (REVISED): the measurement spine on the hook

Not "serve the hook prompt from a flag." Instead: stamp attribution on hook runs; capture the `$ai_trace` + `hook_score` + the human edit-rate for the hook; stand up the offline hook guardrail. One component (the hook) wired through all four spine pieces — then run a real experiment (a hook-rubric variant assigned by a flag) and measure it by **edit-rate**.

### Confirm during implementation

* `@posthog/convex` flag-read API + exact `$ai_*` property names (verify vs the installed package).
* The join `postRuns` ↔ reviewed `contentObjects` ↔ `editEvents` (how a human's edits attribute back to a run + its experiment).
