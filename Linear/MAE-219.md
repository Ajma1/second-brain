## Decision (2026-06-08): standardize on PostHog, not Braintrust

After spiking Braintrust deeply (capture seam **and** prompt versioning — both proven; see repo + `IMPLEMENTATION-PLAN.md`, kept below as context) and evaluating PostHog against our actual needs, we're going with **PostHog** as the LLM-observability + prompt-versioning + experimentation platform, and **building the one missing piece ourselves** (an offline judged-eval CI gate). Braintrust is dropped as a runtime dependency.

### Why PostHog

* Covers most of what we need natively: **AI observability / traces** (`$ai_generation` / `$ai_span` / `$ai_trace`, cost / latency / tokens, OpenRouter support, dashboard), **versioned prompt serving + online A/B** (feature-flag JSON payloads = GA; Prompt Management = beta), **online LLM-judge evals** (sampled live), and **product analytics** — which we want anyway. One vendor, dual-use.
* **Native Convex component** `@posthog/convex` (GA, Convex 1.39+): runs in the **default isolate (no** `"use node"`**)**, capture is **non-blocking** (`ctx.scheduler.runAfter`), so it never sits on the request path. Removes the entire Braintrust runtime headache (REST-from-isolate + outbox/drain).
* `$ai_*` trace events are just events with special property names → emit them via the component's `capture()` (manual-capture path) straight from a Convex action.

### What we build (the one real gap)

PostHog evals are **online/sampled** — there's no packaged **offline dataset → judge → run-vs-run → fail-the-build** gate. So we build a small offline eval gate ourselves with the LLM judge we already have (`hookJudge`).

## Implementation Spec — hook-first slice (2026-06-08)

**Goal:** instrument + version the hook step of the post-writing workflow on PostHog end-to-end — versioned prompt serving + online A/B, an AI trace per run, and an offline judge-gate in CI. One prompt, proving observability + versioning + A/B + CI gating. (Workflow is built + merged: `feat/post-writing-workflow` → `feat/cockpit-phase1`.)

### The version split (key design)

* **Prompt versions live in the repo** (committed, source of truth + reproducible eval ground truth): `convex/lib/methodology/prompts/hook/v1.ts`, `v2.ts`, each exporting `{ version, system, buildUserPrompt(vars), model, temperature }`. `v1` = the current inline hook prompt extracted verbatim (baseline); `v2` = a meaningfully different variant.
* **PostHog serves + A/B-tests them**: a multivariate **feature flag** `hook-prompt` whose JSON payload carries `{ hookPromptVersion: "v1" | "v2" }`; the flag splits traffic → online experiment. (Flag payloads = GA; we deliberately avoid the beta Prompt Management product.)
* So **repo = what the versions are; PostHog = which version a run gets + the experiment.** CI evals the committed versions (reproducible); runtime A/B is native PostHog.

### Components

1. `@posthog/convex` **setup** — `npm i @posthog/convex`; `app.use(posthog)` in `convex.config.ts`; deployment env `POSTHOG_PROJECT_TOKEN`, `POSTHOG_PERSONAL_API_KEY` (flag eval), `POSTHOG_HOST`. Default isolate, no `"use node"`.
2. **Versioned hook prompts (repo)** — `prompts/hook/{v1,v2}.ts` + a `HOOK_PROMPT_VERSIONS` registry + `getHookPromptVersion(id)`. (Pure, unit-testable.)
3. **Variant resolver** — `resolveHookPromptVersion(ctx, {distinctId})`: read the `hook-prompt` flag payload via the component → `{hookPromptVersion}` → look up the committed version. **Fail-open** to `v1` if the flag is unavailable/unknown (never block generation). `distinctId` = client/owner id (stable variant per client).
4. `hookStep` **wiring** — resolve version → render per archetype (existing best-of-N) → generate (existing `Generate` seam) → `hookJudge` winner → **emit** `$ai_trace` **(id =** `workflowId`**) +** `$ai_generation` via `capture()` with `$ai_model`, `$ai_provider:"openrouter"`, input/output, tokens, latency + custom props `hook_prompt_version`, `archetype`, `hook_score`, `chosen`. Capture is non-blocking + fail-soft. Returns the resolved version.
5. **Attribution** — add `promptVersions: v.optional(v.record(v.string(), v.string()))` + `aiTraceId: v.optional(v.string())` to `postRuns`; `finishRun` persists `{hook: versionId}` + traceId.
6. **Online experiment** — a PostHog experiment on the `hook-prompt` flag (control v1 / test v2); metric = the captured `hook_score` now, real published-post engagement later. Mostly PostHog config.
7. **Offline judge-gate (the build, CI)** — `scripts/eval/hook-gate.ts` (`tsx`): runs each version (`baseline` vs the PR's `candidate`) over committed fixtures `eval/fixtures/hook/*.json` (topic + profile), scores with `hookJudge`, aggregates, **exits 1 if** `candidate.mean < baseline.mean − threshold`. CI step on PRs touching `prompts/hook/`. Reuses `hookJudge`; real OpenRouter calls (keyed in CI). No external eval vendor.

### Error handling

* Flag fetch fails / unknown version → **fail-open** to committed `v1`.
* Capture fails → non-blocking (scheduled; doesn't affect the workflow result).
* Offline gate → **fail-closed** (CI fails on regression).

### Testing

* **Unit:** `resolveHookPromptVersion` (payload→version + fail-open), the `$ai_*` event builder (property shape), the gate's pass/fail logic, the prompt-version registry.
* **Live:** run the workflow → a `$ai_trace` with `hook_prompt_version` appears in PostHog; `postRuns.promptVersions.hook` + `aiTraceId` set.
* **Gate:** run `hook-gate.ts` over fixtures; assert it fails when the candidate regresses.

### Out of scope (follow-ons)

* Same pattern for body / judge / revise prompts (after the hook proves out).
* PostHog Prompt Management (beta) — using flag payloads instead.
* Real-engagement experiment metric (needs published-post analytics) — start with `hook_score`.
* General analytics rollout.

### Confirm during implementation

* Exact `@posthog/convex` API for reading a flag payload from an action, and the exact `$ai_*` required property names — research-sourced from PostHog docs; verify against the installed package.
* One `$ai_generation` per archetype (richer) vs one aggregate per hook step (cheaper) — default per-archetype; revisit on event cost.

## (Superseded) Original — Braintrust × Convex Evals

> Retained as context. The Braintrust spike was real and de-risked the whole space — it's how we learned the integration shape + the prompt-versioning mechanics, and it directly informed the decision above. Repo + docs kept for reference; **not being productionized.**

Embed Braintrust evals into the Convex agent stack. The eval capture seam for `@convex-dev/agent` + `@convex-dev/workflow`.

Repo: `github.com/modernagencysales/braintrust-convex-evals` — `README.md`, `IMPLEMENTATION-PLAN.md` (the build plan), `DESIGN.md`, `SPIKE-FINDINGS.md`, runnable `spike/`.
