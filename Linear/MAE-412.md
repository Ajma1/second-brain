## Goal

Build a DuckDB SQL planner that chooses sparse engagement samples from high-signal posts rather than enriching every post.

## Files

Create:

* `tooling/corpus/beneficial-adjacency/engagement-sample-plan.mts`

Modify:

* `tooling/corpus/linkedin-beneficial-adjacency.test.mts`

## Work

Implement `buildEngagementSamplePlanSql(options)` to produce an `engagement_sample_plan` table with selected posts by reason:

* `recent_organic_outlier`
* `lead_magnet_outlier`
* `recent_baseline`

Inputs should include max creators, outliers per creator, lead magnets per creator, baselines per creator, whether reactions are included, and run ID. Output should include post/creator identifiers, post URL, sample reason/rank, posted time, outlier multiple, lead magnet flag, template score, expected endpoint set, and `engagement_sampling_priority_score`.

## Constraints

* Sampling is sparse by design and must not run inside the general creator enrichment loop.
* Lead magnets should be included because they are useful, but tagged separately.
* SQL builder should be deterministic for a given corpus and options.

## Verification

Run:

```bash
rtk env HOST_TEST_MAX_LOAD_1M=100 host-test-slot --class focused pnpm exec tsx --test tooling/corpus/linkedin-beneficial-adjacency.test.mts
```

Expected: PASS.

## Acceptance Criteria

* Tests assert the SQL contains the output table, sampling reasons, and priority score.
* Planner can later be wired into the CLI without needing provider calls.
