## Context

The live Railway recovery required Fabro runtime/backend changes that should not remain as one-off local knowledge.

Verified recovery evidence:

* Deployment `b3203845-41e7-48ce-9cef-93a1e0ce2267` succeeded.
* Smoke run `01KS4GV136R7F2NTS8N30ERXFS` succeeded in 7s.
* Codex CLI backend stage used `gpt-5.3-codex-spark` through subscription auth and wrote the expected marker file.

Source commits in the Fabro worktree:

* `8be6c2114` — support Codex ChatGPT auth file in CLI backend.
* `5de14479d` — add `--skip-git-repo-check` for non-git Railway local sandbox directories.
* `e0fdf55f4` — add `--dangerously-bypass-approvals-and-sandbox` because Railway is already the outer trusted sandbox and nested bwrap is not available.

## Scope

* Upstream or formalize the CLI backend behavior in Fabro rather than keeping it as an ad hoc Railway patch.
* Make the external-sandbox behavior explicit and configurable by runtime policy, not hidden in provider-specific command construction.
* Document when Railway-local execution is acceptable and when Daytona/Docker isolation is required.
* Add automated tests for Codex CLI command construction and auth file restoration.
* Keep `procps` in the Railway image or remove the daemon-record dependency on external `ps`.

## Acceptance Criteria

* Fabro has a named runtime policy for command-owned CLIs running inside an already-isolated service/container.
* Codex CLI backend works in non-git workdirs.
* Railway deployment image contains the CLIs and daemon-probing dependencies.
* The Railway CLI auth smoke remains green from a clean deployment without manual `/storage/server.json` repair.
