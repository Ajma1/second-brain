# Task 10: Build graph v2 SQL and recommendation tables

- **Status:** Backlog

## Goal

Build the DuckDB graph and recommendation table layer that turns creator/post/template/audience/embedding signals into product-ready beneficial adjacency rows.

## Files

Create:

* `tooling/corpus/beneficial-adjacency/graph-v2.mts`
* `tooling/corpus/beneficial-adjacency/reports.mts`

Modify:

* `tooling/corpus/linkedin-beneficial-adjacency.test.mts`

## Work

Create DuckDB SQL/report builders for:

* `creator_nodes_v2.csv`
* `creator_edges_v2.csv`
* `beneficial_adjacency_recommendations.csv`
* `creator_audience_edges.jsonl`
* `creator_audience_overlap_edges.jsonl`
* `cluster_coverage_gaps.csv`
* `edge_type_coverage.json`
* `low_confidence_candidates.csv`

Recommendation rows must include recommendation type, suggested action, operator note, score, confidence, scoring version, named score components, penalties, evidence post/edge IDs, known limitations, and blank/pending review status.

## Constraints

* Beneficial adjacency is action-oriented, not generic nearest-neighbor similarity.
* Rows without evidence must be demoted, marked low-confidence, or written to `low_confidence_candidates.csv`.
* CSV writers must force quoting/escaping for commas, newlines, and evidence lists.
* Default reports must not expose raw third-party actor display fields.

## Verification

Run:

```bash
rtk env HOST_TEST_MAX_LOAD_1M=100 host-test-slot --class focused pnpm exec tsx --test tooling/corpus/linkedin-beneficial-adjacency.test.mts
```

Expected: PASS.

## Acceptance Criteria

* Tests validate output schemas and score/evidence requirements.
* Report writers safely serialize complex rows.
* Recommendation rows expose component columns rather than opaque scores.
